Missing Model for Class.getDeclaredFields() Causes Cascading Loss of Virtual Dispatch Resolution

**Note**: This is the artifact of a research project designed to help static analysis developers reason about and localize the unsoundness issues of their tool.

## Description

### Summary

WALA does not model reflective field discovery through `Class.getDeclaredFields()`. As a result, `Field` objects returned by this API are not introduced into pointer analysis.

When such `Field` objects are passed through application code and subsequently used as receivers of virtual method calls (e.g., `Field.getName()`), WALA cannot determine their concrete type because the points-to set is empty. This missing receiver information propagates transitively through subsequent method calls.

Consequently, method invocations that depend on values derived from reflective field metadata may be omitted from the generated call graph.

## Observed Behavior

* WALA processes calls to `Class.getDeclaredFields()`

* However, the returned `Field[]` contains no modeled `Field` objects

* The receiver parameter of:

  ```java
  field.getName()
  ```

  therefore has an empty points-to set

* Since `Field.getName()` cannot be resolved, the return value is also absent from pointer analysis

* This emptiness propagates through subsequent calls:

  ```java
  field.getName().substring(0, 1).toUpperCase()
  ```

* Consequently, the call graph contains **no edge to**:

  ```
  java.lang.String.toUpperCase()
  ```

## Expected Behavior

For programs that obtain fields via `Class.getDeclaredFields()` and subsequently invoke methods on those fields or values derived from them:

* The analysis should model the `Field` objects returned by `getDeclaredFields()`
* These objects should be propagated through pointer analysis
* Calls such as `Field.getName()` should be resolved
* Return values should flow into subsequent string operations
* A call graph edge should exist, for example:

  ```json
  {
    "caller": "test.simples.Test$2.translateName(Ljava/lang/reflect/Field;)",
    "callee": "java.lang.String.toUpperCase()"
  }
  ```

## Notes on Implementation (inspected behavior)

From code inspection:

* WALA provides a native model for `Class.getFields()`

* The model allocates and propagates reflective `Field` objects returned by that API

* However, there does not appear to be a corresponding model for:

  ```java
  Class.getDeclaredFields()
  ```

  or its native backing method:

  ```java
  Class.getDeclaredFields0(boolean)
  ```

* Because no `Field` instances are allocated for the result of `getDeclaredFields()`, the element points-to set of the returned `Field[]` remains empty

* As a result, parameters receiving those `Field` objects also have empty points-to sets

* During call graph construction, dispatch only occurs when receiver points-to information is available

* Since the receiver set is empty, no dispatch target is generated for:

  ```java
  Field.getName()
  ```

* The resulting absence of return-value information propagates to:

  ```java
  String.substring(...)
  ```

  and ultimately to:

  ```java
  String.toUpperCase()
  ```

Relevant locations:

* `natives.xml`
* `SSAPropagationCallGraphBuilder.java`

In particular:

* `Class.getFields()` has a native model that introduces `Field` objects into the points-to graph
* No analogous model exists for `Class.getDeclaredFields()` or `Class.getDeclaredFields0(boolean)`
* Dispatch in `SSAPropagationCallGraphBuilder` requires a non-empty receiver points-to set before generating call graph edges

## Impact

If the omission of this edge is unintended, it may affect analyses that rely on sound modeling of reflective field discovery.

APIs based on `Class.getDeclaredFields()` are widely used by serialization frameworks, XML processing libraries, dependency injection frameworks, configuration systems, ORM frameworks, and testing tools.

Missing these reflective field objects can lead to:

* Missing call graph edges for reflective field operations
* Incomplete propagation of metadata-derived values
* Cascading loss of precision through subsequent method calls
* Reduced accuracy for framework analyses that rely on reflection
* Incomplete interprocedural information for downstream analyses such as vulnerability detection, impact analysis, and program understanding

Because the missing model originates at a commonly used reflection API, its effects can propagate far beyond the original reflective call site and suppress unrelated downstream call graph edges such as standard library string operations.
