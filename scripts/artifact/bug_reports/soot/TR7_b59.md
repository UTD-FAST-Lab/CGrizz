## Title

Missing call graph edges for reflective field access (`java.lang.reflect.Field.get`)

---

**Note**: This is the artifact of a research project designed to help static analysis developers reason about and localize the unsoundness issues of their tool.

## Description

### Summary

SPARK’s reflection handling in the call graph builder supports only a limited set of reflective entry points, including `Method.invoke`, `Constructor.newInstance`, and `Class.newInstance`. However, it does not include any modeling for `java.lang.reflect.Field` operations such as `Field.get` or `Field.set`.

As a result, reflective field access is not incorporated into call graph construction, and calls to `Field.get(Object)` are ignored in terms of pointer propagation and call edge generation.

---

## Minimal Reproduction

I have attached a Maven-based minimal project that uses `Field.get(Object)` to retrieve a value from a field and subsequently uses it in a typed context.

## Observed Behavior

* SPARK processes reflective calls only for a fixed set of supported reflection APIs
* `Field.get(Object)` is encountered during call graph construction
* However, no reflection model callback exists for field access operations
* The call is therefore treated as an ordinary unresolved library call without pointer effects
* No propagation occurs from the accessed field to the return value
* Consequently, the call graph contains **no edge to**:

  ```
  java.lang.reflect.Field.get(java.lang.Object)
  ```

---

## Expected Behavior

For programs using reflective field access:

* The analysis should include `Field.get(Object)` as a modeled reflection operation
* The returned value should be linked to the heap location corresponding to the accessed field
* Subsequent uses of the returned value should correctly reflect its runtime type
* A call graph edge should exist for the reflective operation, for example:

  ```json
  {
    "caller": "com.example.App.run()",
    "callee": "java.lang.reflect.Field.get(java.lang.Object)"
  }
  ```

---

## Notes on Implementation (inspected behavior)

From code inspection:

* `OnFlyCallGraphBuilder.getImplicitTargets` uses a switch over declaring class names to handle reflection
* Only `java.lang.reflect.Method`, `java.lang.Class`, and `java.lang.reflect.Constructor` are explicitly handled
* There is no case for `java.lang.reflect.Field`
* The `ReflectionModel` interface does not define a corresponding `fieldGet` or `fieldSet` callback
* Consequently, `Field.get` is never translated into pointer constraints or call graph edges
* Instrumentation confirms execution reaches the reflective dispatch switch but falls through the missing case without invoking any modeling logic

Relevant locations:

* `OnFlyCallGraphBuilder.java`
* `ReflectionModel.java`
* `JavaLangReflectFieldNative.java`

---

## Impact

If the omission is unintended, it may significantly affect analyses relying on reflective field access. This pattern is widely used in serialization frameworks, dependency injection systems, ORM libraries, and dynamic configuration mechanisms. Without modeling `Field.get`, the analysis breaks the connection between field storage and subsequent uses, leading to missing call graph edges and reduced precision in interprocedural analysis.
