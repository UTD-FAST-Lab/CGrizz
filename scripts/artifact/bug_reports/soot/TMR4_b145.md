## Title

Missing call graph edges for `MethodHandle.invoke()`-based indirect dispatch

---

**Note**: This is the artifact of a research project designed to help static analysis developers reason about and localize the unsoundness issues of their tool.

## Description

### Summary

SPARK does not model `java.lang.invoke.MethodHandle.invoke()` as a source of precise type flow. The invocation is treated as a regular virtual call returning `Object`, without propagating the target method’s concrete receiver type. As a result, values obtained through method handles are not refined in the pointer analysis, and subsequent virtual calls on those values cannot be resolved.

This leads to missing call graph edges when method handles are used as an indirection mechanism for method or field access.

## Observed Behavior

* SPARK treats `MethodHandle.invoke()` as an unresolved virtual call with no specialized modeling
* No allocation or type flow is associated with the method handle’s underlying target
* The return value of `handle.invoke()` is typed as `Object` with an empty or imprecise points-to set
* Subsequent virtual call resolution on the returned object fails
* Consequently, the call graph contains **no edge to**:

  ```
  cats.tmr4.tmr.Demo.toString()
  ```

---

## Expected Behavior

For programs using `MethodHandle`-based dispatch:

* The analysis should model the linkage between a `MethodHandle` and its underlying target method or field
* The return value of `invoke()` should be refined to the concrete runtime object or value it represents
* Virtual dispatch on values produced by method handles should resolve correctly
* A call graph edge should exist, for example:

  ```json
  {
    "caller": "com.example.App.main(String[])",
    "callee": "com.example.ConcreteValue.toString()"
  }
  ```

---

## Notes on Implementation (inspected behavior)

From code inspection:

* `OnFlyCallGraphBuilder` handles invoke expressions but has no special-case modeling for `java.lang.invoke.MethodHandle.invoke()` or `invokeExact()`
* `virtualedges.xml` does not include any summary that maps method handles to their target methods
* As a result, no constraint is introduced into the pointer analysis for the method handle’s target
* The return value is therefore conservatively typed as `Object`, preventing subsequent refinement during virtual dispatch
* When `getVirtualEdgesMatchingSubSig` returns null, execution falls back to a path that only records the call site without propagating type information

Relevant locations:

* `OnFlyCallGraphBuilder.java`
* `virtualedges.xml`

---

## Impact

If the omission is unintended, it may affect analyses that rely on accurate modeling of `java.lang.invoke`-based indirection mechanisms. Method handles are widely used in modern Java frameworks, lambda metafactories, and dynamic dispatch optimizations. Without proper modeling, call graphs may miss edges involving dynamically resolved method targets, reducing precision for program analysis, security auditing, and dependency tracking.
